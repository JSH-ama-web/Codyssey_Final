# 14. 운영 모니터링 및 오류 로그

> 항목: 무중단 실행·운영 로그·오류 대응 증빙.

## 1. 구성

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| 접근 로그 | `app/observability.py` 미들웨어 | 모든 `/api/*` 요청을 JSON 한 줄로 기록 (request_id, method, path, status, 처리시간 ms) |
| 오류 처리 | 같은 미들웨어 | 처리되지 않은 예외 → 스택트레이스 로그 + 사용자에겐 `request_id`만 반환 (내부 정보 비노출) |
| 요청 추적 | 응답 헤더 `X-Request-ID` | 사용자 오류 제보와 서버 로그를 연결 |
| AI 장애 대응 | `app/agent.py` | Gateway 실패 시 `ai_fallback` 이벤트 로그 + 규칙 기반 로컬 해설로 자동 전환 (서비스 중단 없음) |
| 헬스체크 | `GET /api/health` | 상태, 버전, 배포 커밋, AI 설정 여부(키 값 비노출), 가동시간, 요청/오류 수 |
| 가동 감시 | `.github/workflows/uptime.yml` | 6시간마다 배포 URL의 `/api/health` 호출, 실패 시 Actions 실패로 표시 |
| 서버 로그 열람 | Vercel → Project → **Logs** | 위 JSON 로그를 검색 (`event:ai_fallback`, `status:500` 등) |

## 2. 로그 형식

```json
{"event": "request", "ts": 1795348499.627, "request_id": "78d28d792378", "method": "POST", "path": "/api/analyze", "status": 200, "ms": 34.5}
{"event": "ai_fallback", "ts": 1795348499.626, "task": "water", "reason": "AI 서버 연결 실패: All connection attempts failed"}
```

## 3. 오류 재현 로그 (로컬, 2026-11-22)

AI Gateway 주소를 일부러 닫힌 포트로 지정(`AI_BASE_URL=http://127.0.0.1:9`)하고, 잘못된 입력도 함께 보내 재현했다.

```text
{"event": "request", "ts": 1795348499.589, "request_id": "fbc1b453cecb", "method": "GET", "path": "/api/health", "status": 200, "ms": 2.5}
{"event": "ai_fallback", "ts": 1795348499.626, "task": "water", "reason": "AI 서버 연결 실패: All connection attempts failed"}
{"event": "request", "ts": 1795348499.627, "request_id": "78d28d792378", "method": "POST", "path": "/api/analyze", "status": 200, "ms": 34.5}
{"event": "request", "ts": 1795348499.632, "request_id": "bfa571904f3e", "method": "POST", "path": "/api/analyze", "status": 422, "ms": 0.6}
{"event": "request", "ts": 1795348499.636, "request_id": "914d954340a7", "method": "POST", "path": "/api/analyze", "status": 422, "ms": 0.5}
응답: 422 {'detail': '지원하지 않는 분석 작업입니다.'} X-Request-ID= 914d954340a7
{"event": "request", "ts": 1795348499.639, "request_id": "72166fdeb06a", "method": "GET", "path": "/api/health", "status": 200, "ms": 0.7}
health.runtime: {'started_at': 1795348499, 'uptime_s': 0, 'requests': 4, 'errors_4xx': 2, 'errors_5xx': 0}
```

해석:
- Gateway 연결 실패에도 `/api/analyze`는 **200**으로 응답했고, `ai_fallback` 로그가 남았다 → AI 장애가 서비스 중단으로 이어지지 않음.
- 빈 전단 데이터·지원하지 않는 시험 유형은 **422**와 한국어 오류 메시지로 거부되었고 `errors_4xx`로 집계되었다.
- 5xx 오류는 0건.

## 4. 장애 대응 절차

1. Uptime 워크플로 실패 알림(GitHub 메일) 또는 사용자 제보 수신
2. `/api/health` 직접 호출 → `status`, `ai_configured`, `commit` 확인
3. Vercel Logs에서 제보받은 `X-Request-ID` 또는 `status:500` 검색
4. 원인 수정 → 브랜치·PR → CI 통과 → main 병합 → Vercel 자동 재배포
5. 이 문서의 운영 기록표에 기록

## 6. 한계

- Vercel 서버리스 인스턴스는 요청이 없으면 내려갔다 다시 뜨므로 `uptime_s`·요청 수는 인스턴스 단위 값이다. 장기 가동률은 Uptime 워크플로 기록으로 판단한다.
- SQLite는 `/tmp`에 저장되어 인스턴스 교체 시 초기화된다. 영구 저장은 외부 DB 전환이 필요하다.
